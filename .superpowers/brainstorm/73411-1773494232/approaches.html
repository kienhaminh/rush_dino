Implementation approaches

All options use the same UI (segmented control in card header). The difference is how the backend stores & applies the override.

A

Override field in AppState RECOMMENDED

Add a Arc<RwLock<Option<ThinkingLevel>>> to AppState. The react_loop checks this override first, falling back to the engine's static config. A new PATCH /api/system/thinking-level endpoint sets it.

Pros

  • Minimal change to engine internals
  • Clear "override" semantics
  • Easy to reset (set to None)

Cons

  • Two places to check for thinking level (override → config fallback)
B

Mutable field on AgentEngine

Change thinking_level inside AgentConfig to Arc<RwLock<ThinkingLevel>>. Add a set_thinking_level() method on the engine. Single source of truth.

Pros

  • Single authoritative source
  • Cleaner — no fallback logic

Cons

  • Changes AgentConfig struct shape
  • All callers of config.thinking_level need a .read() call
C

Frontend-only optimistic state (no backend change)

Store the override in React state, send it as a query param or header on each chat message. The backend reads it per-request — no engine mutation needed.

Pros

  • Zero backend struct changes
  • Reset is automatic on refresh

Cons

  • Requires modifying the chat WebSocket protocol
  • Thinking level shown in Sessions page won't reflect the override
